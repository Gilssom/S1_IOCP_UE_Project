# S1 복구·AWS 배포·운영 Agent 단계별 검토안

2026-10-08 후속 승인: S1만 Private Git 등록·로컬 작성자 설정·원격 업로드를 승인했고, 이후 사용자가 실제 에셋 파일은 제외하고 README에 사용 목록만 기록하도록 범위를 변경했다. 소스 전용 정책은 GitManagement.md 참조. 아래 Git 미승인/미실행 표현은 이전 기획 시점 기록이다. AWS/DB/전체 복원·Agent 변경은 여전히 미승인이다.

작성: 2026-10-07. 상태: 검토용 기획. Git 초기화, 대량 추적, 백업 실행, AWS 생성/배포, DB 변경, Agent 권한 부여는 승인·실행하지 않았다. 구현 담당에게 후속 메시지도 보내지 않는다.

## 현재 기준과 목표

InventoryWidgetBlueprint.md와 QuickSlotsImplementation.md 및 실제 US1InventoryWidget/US1InventoryStackWidget 선언을 확인했다. 퀵슬롯 숫자키 수정 및 Widget Blueprint 전환, 인벤토리 창/행 디자인 분리가 현재 기준이다. 최신 인벤토리 PIE 조작은 사용자 인수이며 인원수와 모든 세부 조건이 특정되지 않았다. 빌드·자동화20개·패키징 성공은 문서상의 실행 기록이며 이번 기획에서 재실행하지 않았다. 인증된 패키지 2계정 전체 인수는 미검증이다.

S1_UE5.8/.git 없음 확인. 기존 서버 저장소와 부분 체크포인트는 있으나 통합 복구 시험 완료를 뜻하지 않는다. ServerCore/IocpCore.cpp의 CreateIoCompletionPort/GetQueuedCompletionStatus 및 Session.cpp의 WSARecv를 확인했다. Windows 의존성이 있으므로 첫 배포는 Windows EC2를 우선 후보로 하고 Linux 이전을 전제하지 않는다. DB 드라이버·런타임·서비스 실행 방식은 배포 조사에서 추가 확인한다.

사용자와 합의한 최소 원칙: 평소에는 변경 파일/에셋 부분 백업, DB 변경 때 DB 백업, 큰 작업·촬영 전 전체 기준점. 지금 전체 Unreal/서버/DB 통합 백업을 의무적으로 실행하지 않는다. 단 같은 PC의 부분 복사본은 디스크 손실까지 막지 못한다는 제한을 기록한다.

## 복구 대상과 하나의 버전 묶음

각 기준점은 하나의 ReleaseId로 다음을 연결한다. 아직 자동 도구를 만들 필요는 없고 작은 Markdown/JSON 목록부터 시작한다.

| 대상 | 기록·보관 내용 |
|---|---|
| Unreal | Source, Config, .uproject, 프로젝트 Plugins의 소스/설정/필요 binary, Content 및 필요한 .ubulk/.uexp 등 동반 파일, 엔진 버전/빌드 방식 |
| 외부 서버 | 소스 revision 또는 변경파일 해시, 실행파일/의존 DLL, 빌드 구성, 실행 인수·작업 디렉터리 |
| 계약 | canonical .proto와 생성기 버전, 생성물 해시, client/server combat·loot·use 계약 대응, DB migration 버전 |
| 맵 연계 데이터 | 저장된 MainMap 기준, .nav/.spawn/.lootobb 원본 export와 배포본의 해시·경로, export 시각/도구 버전 |
| DB | 백업 식별자/시각/범위/복원방법, migration 목록. 접속 암호·백업 원문은 일반 문서에 넣지 않음 |
| 플레이 설정 | 캐릭터별 로컬 퀵슬롯 저장 필요 여부. 재생성 가능한 테스트 설정과 보존할 사용자 설정 구분 |
| 검증 | 빌드/PIE/패키지/복원 결과, 실행자·시각, 사용자 인수와 도구 검증 구분 |

Saved/Intermediate/DerivedDataCache 전체를 무조건 버전관리하지 않는다. Saved 내 사용자 SaveGame·진단증거·배포아티팩트 등 필요한 항목은 별도로 선별한다. vendor binary-only plugin은 재빌드 불가 여부를 먼저 확인한다. 에셋 라이선스와 비밀정보 검사를 거쳐 비공개 저장소/백업을 사용한다.

## 단계 0 — 로컬 변경을 작게 되돌릴 수 있게 만들기

- 시작: 지금, 다음 일반 작업부터. 전체 백업 없이도 진행 가능.
- 목표: 실수한 파일/에셋 변경을 복원하고 어떤 서버·클라이언트 조합이 검증됐는지 찾기.
- 최소 산출물: 변경 전 파일 목록+복사본+SHA256, 변경 목적/결과, ReleaseId 대응 목록 초안, 부분 복원 절차 한 장.
- 버전관리 후보 A: S1 비공개 Git + binary 에셋 Git LFS, 서버는 기존 Git 유지. LFS 용량/호스팅 요금/다운로드·복원 비용과 콘텐츠 용량을 먼저 조사. LFS는 binary 변경 내용을 자동 병합하거나 DB를 백업하는 기능이 아니다.
- 대안 B: S1 소스/Config/프로젝트 plugin은 Git, Content는 버전별 manifest+외부 저장소 증분 백업. 당장 대용량 LFS 업로드 부담은 줄지만 코드와 에셋 버전 대응을 별도 지켜야 한다. binary-heavy 팀 작업이 실제로 생기면 Perforce 등 검토; 지금은 도입하지 않는다.
- 권장: 용량 조사 후 A/B 중 선택. 기존 부분 백업은 즉시 폐기하지 않는다. Git 저장소만 같은 디스크에 만드는 것으로 장비 고장 복구가 완성되지 않는다.
- 사용자: 저장 위치/비공개 원격 사용/용량 예산 결정, 미저장 에셋의 보존 선택. Git 초기화·대량 추적은 별도 승인.
- 구현 담당: ignore/LFS 대상 제안, 민감정보 제외, manifest 작성 및 복원 절차 검증. 기존 변경을 reset/clean하지 않음.
- Agent 허용: 요청된 파일 조사·변경 전 사본 생성 등 현 작업 범위. 임의 저장소 공개·대량 삭제 없음.
- 인수: 원본을 건드리지 않는 임시 폴더로 작은 코드/에셋 묶음을 복원해 해시 확인, 참조 의존성을 갖춘 별도 검사 환경에서 로드/빌드 확인. 이 시험을 전체 프로젝트 복원 성공으로 보고하지 않음.
- 상대 작업량: 작음. 최초 전체 Content 인벤토리/원격 업로드는 용량에 따라 중간 이상.

## 단계 1 — AWS 테스트 서버를 재현하고 이전 빌드로 돌아가기

- 시작/선행: 외부 접속 시연을 결정했을 때. 로컬의 검증된 client/server 한 쌍, 버전 manifest, AWS 예산/리전/접근 승인 필요.
- 목표: 한 대의 테스트 서버 배포와 이전 검증 빌드 복귀. 자동 확장/멀티리전/대형 CI·IaC는 제외.
- 환경 후보: Windows EC2 + 서버 실행파일. MySQL은 같은 테스트 VM과 RDS 중 비용/백업 부담을 비교한 뒤 선택. RDS 전환은 ODBC 연결·권한·버전·트랜잭션 호환성 검증 후 결정. 같은 VM은 장애 범위가 서버/DB에 걸친다는 제한이 있다.
- 최소 산출물: ReleaseId별 아티팩트/해시, 환경설치 목록(OS/VC++ runtime/ODBC/DB버전), 비밀정보를 뺀 설정 템플릿, 시작/상태확인/정지 절차, 수동 배포·복귀 절차, DB 백업·복원 절차.
- 구성: 가능하면 버전별 디렉터리 배포 후 선택 전환. 배포 전 새 접속/쓰기 중단과 pending 소비·획득 처리 정책 확인, 로그/DB 상태 확보, 호환 버전 전환, 준비상태 확인, 접속 재개. exe를 덮어쓰는 것만으로 배포 완료라 하지 않는다.
- 게임 포트와 관리 접근을 구분하고 관리 포트의 무제한 공개를 피한다. 인스턴스 역할/짧은 자격증명, 비밀 저장소 또는 보호된 환경 설정 사용. 비밀을 Git/아티팩트/프롬프트에 넣지 않는다.
- 사용자: AWS 계정·리전·월예산·가동시간·DB 선택 및 배포 승인. 자격증명은 안전한 계정 UI로 설정.
- 구현 담당: 실제 Windows/ODBC 의존성 검사, 최소 실행서비스 또는 감독 프로세스 선택, 설치/배포·복귀 스크립트, 새 환경 검증.
- Agent 허용: 아직 운영 변경 권한 없음. 승인된 테스트 배포 작업만 수행.
- 인수: 깨끗한 테스트 인스턴스에서 재현, 서로 다른 두 클라이언트 로그인/전투/획득/사용/재접속, 이전 빌드 복귀 후 호환성 확인. 포트 열림이나 NullRHI 종료 성공은 대체 증거가 아니다.
- 상대 작업량: 중간. 처음 ODBC·네트워크·패키지 호환 문제에 따라 증가. 비용은 Windows 실행시간, VM/DB, 디스크·snapshot·로그·아티팩트·전송량·공인IP 등을 산정한 뒤 추정한다. 정지 상태도 일부 저장 자원 비용은 남을 수 있다.

## 단계 2 — 보존할 플레이 데이터 운영과 실제 복원 시험

- 시작/선행: 잃으면 안 되는 플레이어 데이터를 받기 전. 단계1과 사용자 RPO/RTO 선택 필요.
- 목표: RPO(허용 데이터 손실 시간), RTO(복구까지 허용 시간)를 측정 가능한 정책으로 만들기.
- 초기 검토값: 폐기 가능한 테스트는 일일 백업·RPO24시간/RTO반나절도 선택 가능. 보존할 데이터는 예컨대 RPO15분/RTO2시간을 목표 후보로 검토하되 실제 복원 시험 전 보장하지 않는다. 요구가 강할수록 비용/구조 증가.
- 최소 산출물: 자동 백업 주기·보존기간·암호화/키 복구·접근정책, 백업 실패 경보, 별도 환경 복원 보고, schema 호환표, 장애 대응 절차. 보존안 예시는 일간7개+주간4개이며 확정값이 아니다. PITR은 백업과 transaction log 보관/연속성이 필요하다.
- DB 일관성: Item만 따로 과거로 되돌리지 않고 ItemUseOperation/InventoryState/요청결과/지급원장/outbox 등 관련 테이블을 일관된 지점으로 복원한다. 외부 JSONL 이벤트와 EventId/중복/복원 전후의 데이터 계보를 확인한다. 포션의 승인된 crash 반환 정책은 남으며 복원이 DB+런타임HP exactly-once를 제공하지 않는다.
- RDS 선택 시 PITR은 원본을 바꾸지 않는 새 DB 인스턴스로 복원된다. 설정/접근권한·데이터 검증 뒤 연결 전환을 별도로 수행한다. 직접 설치 MySQL은 일관된 백업과 필요 시 binlog 기반 복구를 설계·검증한다.
- 코드 rollback과 DB restore를 분리한다. 기본은 새 schema에 구/신버전이 공존할 수 있는 추가형 migration과 forward fix. 파괴적 migration은 별도 승인. 구버전이 현재 schema/계약을 읽을 수 없으면 실행파일만 되돌리지 않는다.
- 데이터 장애는 쓰기 중단→현재 상태 별도 보존→새 DB로 복원→백업 시점 이후 거래 차이 확인→사용자 승인→연결 전환. 운영 DB에 과거 백업을 곧바로 덮어쓰거나 수량을 임의 감산하지 않는다.
- 사용자: RPO/RTO·보존기간·데이터 손실/전환 승인. 구현 담당: 자동백업/복원 검사 및 런북. Agent: 백업 상태 읽기·알림만, 운영 복원/삭제 금지.
- 인수: 예컨대 월1회 및 중요 migration 후 별도 DB 복원 시험; 로그인·아이템잔액/원장·중복요청/사용복구·호환패킷 확인, 실제 소요/손실 구간 기록. DB 스냅샷 생성 성공만으로 통과하지 않는다.
- 상대 작업량: 중간~큼. 데이터 중요도·규모·PITR 필요성에 비례.

## 단계 3 — 읽기 전용 운영 AI Agent

- 시작/선행: 배포·구조화 로그·기본 장애 경보와 복구 절차가 먼저 존재할 때. 현재 outbox/원장의 의미를 유지.
- 목표: 장애 원인 후보와 근거 이벤트를 정리하고 운영자에게 알림. 자동 수정은 하지 않음.
- 최소 산출물: 읽기 전용 역할/로그 view, 민감정보 제거, 조회범위/보존/호출량 제한, 구조화 경보 요약, 평가용 정상/비정상 사례.
- 관찰: 접속 실패율, DB대기/오류, pending 소비, 동일DropId 중복 성공, 원장불일치, 서버·디스크 자원. 동일 몬스터 종류 반복 사냥만으로 부정행위 단정 금지.
- 직접 운영 DB 전체를 열기보다 제한된 조회/집계 또는 로그를 사용. 계정 비밀번호/토큰/백업 원문은 모델에 제공하지 않음. 로그와 사용자 생성 문자열은 지시가 아닌 데이터로 취급.
- 사용자: 알림 수신처·민감정보 범위·모델/API 예산 승인. 구현 담당: 마스킹·도구별 권한·평가/알림 구현. Agent: 조회·요약·권고만; shell/배포/SQL쓰기/IAM변경 없음.
- 인수: 실제/합성 장애에서 증거ID를 제시하고 추정을 구분, 정상 사냥 오탐 점검, 악성 로그 문구가 권한 변경/명령 실행으로 이어지지 않음, 쓰기 API 부재 및 권한 거부 확인.
- 상대 작업량: 중간. 토큰량은 로그 원문 대신 집계·관련 이벤트만 보내고 이벤트 기반 실행/중복 경보 억제로 제한. 매프레임/상시 전체 로그 전송 금지.

## 단계 4 — 제한된 변경 Agent

- 시작/선행: 읽기 전용 Agent의 유용성과 오탐을 확인하고, 허용 작업별 수동 복구가 검증된 뒤. 선택 단계이며 포트폴리오에 필수 아님.
- 목표: 좁은 반복 복구만 자동화. 모델에 관리자 shell이나 포괄 AWS 역할을 주지 않음.
- 최소 산출물: typed action allowlist, 환경/리소스 ID 제한, dry-run 계획, 사전조건·사후검사, 사람 승인 token, 감사기록, kill switch와 독립 권한 철회 경로.

| 작업 | 초기 정책 |
|---|---|
| 상태조회·보고 | 자동 허용 |
| 비파괴 진단 수집 | 한도·마스킹 내 허용 |
| 테스트 서버 재시작 | 승인된 런북과 데이터작업 drain/health 조건 만족 시만 허용 후보 |
| 배포·이전 빌드 복귀 | 초기에는 건별 사람 승인, 승인된 아티팩트 해시만 사용 |
| 운영 프로세스 재시작 | 진행중 거래·가용성 영향 검토 및 초기 건별 승인 |
| DB 쓰기·보상 지급 | 별도 좁은 API/증거/사람 승인, 임의 SQL 금지 |
| DB 복원·파괴, IAM·방화벽 변경 | 자동화 제외, 별도 사람 승인과 실행 범위 재검토 |
| 백업 삭제·보존정책/암호키 변경 | Agent 권한에서 제외 |

- 재시작 예시 제한: 30분 내1회 후 미복구면 자동작업 중단·사람 호출. 수치는 승인 때 확정. 동일 장애 중복 action lock, 전체 횟수/시간/비용 한도, 쿨다운, circuit breaker 필요.
- 검증 실패 시 사전 승인된 호환 코드/설정으로만 되돌린다. DB restore를 일반 rollback으로 자동 실행하지 않는다. 반복 재배포↔rollback 루프 금지. 불확정 거래가 있는 상태는 먼저 readback/수동 진단.
- 사용자: 허용작업/위험도/승인자 결정. 구현 담당: 모델 외부의 정책 검사·감사·rollback 검증. Agent: 허용된 호출만 요청; 자신의 권한/예산/백업을 변경할 수 없음.
- 인수: dry run→격리환경 장애주입→사람 승인 실행 순서. 금지작업 차단, 재시작폭주 중단, kill switch, stale approval/다른리소스 거부, 복구실패 감사기록 검증.
- 상대 작업량: 큼. 먼저 한 작업(테스트 프로세스 재시작)만 허용하는 것이 적절.

## 지금 할 최소 항목과 미룰 항목

지금 권장(실행은 별도 요청): 기존 부분 체크포인트에 변경목록/해시/복원법을 갖추고, 큰 작업·촬영 전 하나의 ReleaseId로 검증 조합을 기록. 다음 DB 변경 전 일관된 DB백업 및 별도복원 확인. 버전관리 방식 선택을 위한 Content 용량·민감파일 범위 조사부터 한다.

AWS 준비 때: EC2/DB/리전/가동시간 선택, 아티팩트 저장·비밀관리·네트워크·배포복귀, 예산 알림. 실제 데이터 수용 전: 자동백업/RPO/RTO/복원시험. 운영 로그가 쌓인 뒤: 읽기전용 AI. 변경 Agent는 마지막 선택사항.

지금 하지 않을 것: 전체 프로젝트 대량 업로드, AWS 리소스 생성, 관리형 DB 강제 이전, Linux 포팅, Kubernetes/멀티리전/대형 CI, 전체 운영 권한 Agent.

## 결정이 필요한 항목 / 비용 전제

1. 가까운 시일의 목적: 로컬 촬영 유지 vs 외부 AWS 테스트 일정.
2. Git+LFS 또는 소스Git+Content 별도 버전백업, 비공개 저장 위치/용량 예산.
3. AWS 리전·월 예산·테스트 가동시간 및 DB 같은VM/RDS 비교 선택.
4. 실제 데이터 보존 필요 시 RPO/RTO·보존기간·승인자.
5. Agent는 읽기전용부터 시작하고 알림/API 비용 한도 결정.

상대 작업량은 담당1명, 현재Windows/IOCP+MySQL·테스트서비스1개·리전1개를 가정한다. 시간/토큰/AWS월비용은 파일·DB용량, 가동시간, 모델/로그량, 복구 목표를 조사한 뒤 추정한다. 확정 견적은 제시하지 않는다. AWS Budgets 알림은 지출의 즉시 하드캡이 아니다. 저장소/로그 보존과 Agent 호출 상한을 별도로 정하고 지연 청구/알림을 고려한다.

## 공식 근거 (2026-10-07 확인)

- AWS는 데이터뿐 아니라 애플리케이션/설정도 RPO/RTO에 맞춰 백업하고 주기적 복원으로 절차를 검증하도록 권고한다: [Well-Architected 백업](https://docs.aws.amazon.com/wellarchitected/latest/reliability-pillar/back-up-data.html).
- AMI는 부팅 소프트웨어 구성이며 OS/리전/아키텍처에 종속된다. 본 문서의 Windows EC2 우선안은 로컬 IOCP 소스에 근거한 설계 제안이다: [EC2 AMI](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/AMIs.html).
- RDS PITR은 원본을 변경하지 않고 새 인스턴스를 만든다. 복원 후 설정/접속 전환을 검증해야 한다: [RDS 시점 복원](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/USER_PIT.html).
- 최소권한과 임시 자격증명을 우선한다: [IAM 모범 사례](https://docs.aws.amazon.com/IAM/latest/UserGuide/best-practices.html).
- 비용 모니터링/알림은 예산 관리 수단이며 절대 지출 차단 보장이 아니다: [AWS Budgets](https://docs.aws.amazon.com/cost-management/latest/userguide/budgets-managing-costs.html).

변경 결과: 이 검토 문서만 추가. 실제 복구/배포/권한 도구를 실행하거나 성공했다고 주장하지 않는다.
