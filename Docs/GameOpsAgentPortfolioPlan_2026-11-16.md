# GameOps Agent 구현 및 자기소개서 근거 계획

2026-11-16 기획 전달본. 사용자 요청은 기획 정리 및 구현 담당 전달이다.
이 문서 자체는 Agent 구현 완료, 신규 DB/프로토콜 변경 또는 유료 API 사용 승인이 아니다.

## 목표와 현재 근거

공통 포트폴리오 설명: C++ IOCP 게임 서버의 이상을 감지하고 Python Backend와
AI Agent가 서버 지표·거래 기록·필요한 게임 화면을 조사해 근거 보고서를 만드는 시스템.
게임 서버/백엔드/AI 지원에 동일한 문제와 설명을 사용한다.

확인한 근거: ObservabilityLoadBaseline_2026-11-16.md,
ObservabilityRepeatedLoad_2026-11-16.md, AuthAndQueueMetrics_2026-11-16.md,
구현 채팅의 최신 결과. 이번 기획 작업에서 부하 시험을 새로 실행하지 않았다.

현재 실제 성과:
- 비밀번호 검증 중 DB 연결 반환으로 점유를 줄임. 로컬 Debug 격리 32명 시험의
  풀4 단일 비교에서 입장 4/32→28/32, 이후 반복 27/32씩 확인.
  풀8의 반복 32/64명은 전원 입장했으나 실제 입장자 수/월드 상태 및 생성기 편차가 있어
  성능 인과나 수용량 보장으로 확대하지 않는다. 기본 풀4는 유지했다.
- 길이0 프레임의 반복 파싱과 분할 수신 잔여 버퍼 문제를 수정하고 격리 회귀 검사.
- 단계별 DB 획득 실패, 해시 시간, 전체 작업 큐 대기 계측 추가.
  최신 계측은 별도 시험 바이너리에서 검증했으며 일반 서버 적용/PIE는 별도다.
- 전체 작업 큐 지연만으로 Room/이동/AI/DB 중 원인을 확정할 수 없다.

아직 성과로 쓸 수 없는 것: AOI/관심 영역 전송 제한, 이동 병합, 송신량 감소율,
대규모 서비스 수용량, Agent/VLM 완성. 앞선 자기소개서의 해당 문장은 가정 초안이다.

## 구현 경계

Unreal C++↔GameServer C++↔기존 MySQL의 게임 권위를 유지한다.
확정 이벤트/지표→Python 수집·조회 Backend→조사 Worker/Agent→보고서·대시보드.
필요시 Unreal 캡처→Backend→VLM 도구로 연결한다.
Agent/모델 응답을 게임 처리에서 기다리지 않는다. Agent 중단/모델 실패에도 게임은 동작한다.
처음은 Python 프로젝트 하나에서 API/수집/Worker 모듈을 나눈다. 기술 스택·새 폴더 위치는
조사 후 제시. Kafka/Kubernetes/복수 Agent/벡터DB/AWS는 첫 단계 필수가 아니다.
Agent는 제한된 읽기 도구만 사용한다. DB쓰기/보상/제재/프로세스 재시작/임의 SQL·shell은 제외.
운영 대응의 의미는 감지·조사·보고이며 자동 복구를 구현했다고 표현하지 않는다.

## 단계 1: 기존 지표 기반 운영 조사 MVP — 먼저 완성

목표: 접속 변화, DB 풀 부족, 큐 지연, 프레임 오류를 기존 JSONL/텍스트 로그로 조사.
모든 성능 병목 해결이나 거래 로그 전면 개편을 선행 조건으로 두지 않는다.

Backend:
- 지표 파일 tail 및 과거 run 재생. 서버 실행 식별자(PID+시작시각 등), UTC,
  원본 위치/수집 시점/테스트 조건 연결. 재시작 카운터 reset, 반복 읽기 중복,
  파일 교체/부분 마지막 줄, 누락·역순 데이터에 대한 정책과 상태 기록.
- 누적값 차분·시간당 비율·버킷 통계는 코드로 계산. 샘플이 없으면 정상으로 판정하지 않음.
  5초 관측의 짧은 피크 누락, 상한 버킷, 성공자만 포함한 p95 등 측정 한계를 보존.
- 간단한 규칙으로 조사 후보 생성. 임계값/최소 표본/유예·중복경보 억제는 설정으로 관리.
  DB 부족 횟수 증가, 비정상 프레임 차단, 지속 큐 지연을 우선. 임계값은 임시 기준임을 표시.
- 조사 작업의 대기/실행/성공/실패·시간제한과 재실행 중복방지, 원본 근거 보관.
- DB를 새로 만들기 전 로컬 Agent 저장소 후보와 보존 범위를 제출. 게임 DB 일반 재설계 불필요.

Agent 도구(typed/조회 범위 제한): 실행별 지표 조회, 전후 구간 비교,
관련 로그 조회, 승인된 지표 정의/런북 조회. 필요한 도구를 결과에 따라 추가 선택한다.
로그는 명령이 아닌 데이터다. 비밀번호/토큰/패킷 본문을 모델에 전달하지 않는다.
출력: 관측 사실, 원인 후보, 반증/부족 근거, 권장 확인, 실행ID·시각·파일/이벤트 참조.
확정 사실/가설/판단불가를 구분. CPU·DB·큐의 상관을 인과로 단정하지 않는다.
모델 실패시 규칙 결과와 조회 가능한 근거는 남기고 AI 조사 실패로 표시한다.

최소 화면: 경보 목록, 해당 구간 지표, 조사 순서/도구 결과, 근거 링크 보고서.
모델/API 선택·비용 한도·키 설정은 사용자 선택 사항이다. 키는 안전한 환경 설정으로 받는다.
모의 모델은 명시하고 실제 모델 동작 성공으로 보고하지 않는다.

단계1 인수:
- 기존 정상/부하/프레임 오류 자료의 재생으로 실제 현상과 데이터 한계를 설명.
- 정상 고부하와 DB 부족 거부, 잘못된 프레임 차단, 근거 부족을 구분.
- 동일 입력 중복 처리/서버 재시작/깨진 줄/로그 내 악성 지시/모델 시간초과 검증.
- 소수 live 이벤트를 읽기전용 수집해 재생과 현재 데이터를 UI에서 구분.
- 최종 평가용 실행은 개발용과 분리. 규칙 단독/Agent 비교, 경보 정밀도·재현율,
  근거 정확성·근거 없는 주장·판단유보, 조사 시간·호출 수·비용을 측정.
  표본 수를 기록하고 작은 fixture 결과를 일반 정확도로 과장하지 않는다.

## 단계 2: 아이템·퀘스트 거래 조사 — 공통 시나리오 확장

기존 outbox/EventId/RequestId/DropId/지급 원장/보상 기록의 현재 구현과 누락을 먼저 조사.
필요한 읽기 view/API와 최소 이벤트 보강을 제시하고 새 계약/DB변경은 구체화 후 승인.
규칙 코드는 중복/수량 불일치 계산, Agent는 거래의 추가 조회 및 원인 후보 보고 담당.
정상 반복 사냥을 부정행위로 단정하지 않는다. 로그 중복 발행과 실제 중복 지급 구분.
시연: 정상 지급, 중복요청을 서버가 방어, 격리 합성 이상 거래의 근거 조사.
운영 DB를 일부러 훼손하지 않으며 실제·재생·합성 자료의 출처를 표시한다.
인수: 근거 ID 연결, 정상 반복 사냥 오탐, 승인 거절과 성공 구분,
단계1 회귀 및 게임 응답 경로에 추가 AI 의존성이 없는지 확인.

## 단계 3: VLM 화면 교차 검증 — 범위 제한

퀘스트 보상 1개 흐름만: 보상 전후 화면과 해당 서버 확정 기록 비교.
사용자 직접 플레이, 이벤트/RunId/캐릭터/캡처 시각 연결, UI 반영 대기·판단유보 정책.
가려짐/낮은 해상도/늦은 캡처/숫자 오독은 판단불가 가능. 정확한 수량 판정은 서버/코드.
보상 UI와 인벤토리 갱신의 시각적 불일치 의심을 보고하고 추가 확인을 제안한다.
자율 게임 조작·연속 영상 전체 해석·모든 UI 검사·자동 버그 수정은 제외.
인수: 정상/갱신 누락/의도적 지연/가림 사례, VLM 추가 전후 발견율과 오탐·비용 비교.
캡처·계정정보 최소화 및 모델 전송 범위를 확인. 기존 Unreal UI/캡처 도구 재사용 우선.

## 자기소개서와 결과물

사용자는 Agent 완성 시점을 기준으로 700자 자기소개서를 준비한다.
현재 초안과 최종 실적을 구분하고 단계 완료 전 이력에 완료 성과로 확정하지 않는다.
서사: 동시 접속에서 DB 자원 점유 문제 발견→연결 수명 수정·격리 반복 측정→
프레임 안정성 수정→관측 기반 마련→Agent가 지표/거래를 도구로 조사하고 근거 보고.
VLM은 단계3 완료 시에만 실적으로 포함. AOI/송신 최적화는 별도 실측 구현 때 추가.
성능 측정은 동일 조건 반복, 성공률과 성공 응답 지연 동시 기재,
Debug/루프백/동일PC/생성기 제약 기록. 해시 보안 강도를 낮춰 얻는 성과는 제안하지 않는다.

최종 산출물: 아키텍처1장, 재현 가능한 테스트/실행 가이드, 비교 측정표,
Agent 평가표, 근거 포함 보고서 예시, 게임+운영화면 시연 영상, 한계와 버전 manifest.
각 단계 종료 시 변경 파일/테스트/사용자 인수/미검증/실행 버전 보고.
기존 수정·GameServer staging 보존, 자동 커밋/푸시 및 무단 에셋 이관 없음.

## 구현 담당에게 요청할 바로 다음 작업

현재 소스·지표 스키마와 로그 경로를 읽고 단계1의 최소 설계/정확한 변경 파일,
Python 작업 위치, 재생 자료 목록, 실제 모델 연결에 필요한 사용자 선택을 정리한다.
앞선 자소서의 가상 트래픽 성과를 실제 작업 이력으로 혼동하지 않는다.
추가 병목 최적화 완료를 기다리지 않고 단계1부터 검증 가능한 크기로 진행안을 제시한다.
이번 기획 전달을 전체 단계 실행·운영 DB변경·유료 호출 승인으로 확대하지 않는다.
