## 조건

- 기존 기준선과 수정 내용은 `ObservabilityLoadBaseline_2026-11-16.md`를 참고한다. 이번에는 동일 서버 실행 파일(SHA-256 `F91E9B3FFF13546FB569D7A8BB1F7765FD76660CAC10662358082DD5CA9552C2`)로 DB 풀 4와 8을 각각 격리 실행했다. 일반 서버의 기본 풀 크기 4는 바꾸지 않았다.
- 서버는 로컬 7778, 테스트 DB `S1LootTest_20261001`을 사용했다. 부하 생성기·서버·DB 및 실행 중인 다른 앱이 같은 컴퓨터를 공유했다. 두 조건의 내비게이션·스폰·포털·획득 장애물 데이터는 파일 해시가 같았다.
- 조건별로 계정과 캐릭터를 미리 만들고 동일한 테스트 계정 집합으로 3회 시험했다. 연결을 먼저 맺은 다음 로그인 요청을 보내며, 각 회차 최초·최종 요청의 전송 시각 차이는 약 1~5ms였다. 입장 성공자는 마을 이동, 포털 이동, 필드 이동 및 1.6초 간격 기본 공격을 했다. 테스트 계정은 격리 DB에 남아 있고 비밀번호는 결과 파일에 기록하지 않았다.
- 이전의 요청 동기화 전 탐색 실행은 아래 비교에서 제외했다. 각 수치는 개별 회차의 p95이며 세 회차 결과를 합친 p95가 아니다. 로그인 p95는 성공 응답만 포함한다.

## 로그인 비용과 해석

현행 로그인 핸들러는 계정 조회 뒤 DB 연결을 반환하지만, IOCP 수신 작업 스레드에서 PBKDF2-SHA256 210,000회 비밀번호 검증을 동기 수행하고 이후 캐릭터 조회를 위해 연결을 다시 획득한다. 따라서 해시 계산은 네트워크 작업자 점유의 가능한 원인이며, 풀 부족 응답이 어느 획득 단계에서 났는지는 기존 지표만으로 구분하지 못한다.

동일 PC에서 가짜 비밀번호를 사용해 같은 Windows BCrypt 알고리즘을 별도로 시험한 결과, 1개 작업자·15회에서 평균 56.390ms, p95 57.340ms였고, 5개 작업자·30회에서 평균 62.350ms, p95 64.950ms, 전체 처리량은 약 78.32회/초였다. 이는 독립 미세 측정이며 서버의 실제 큐 대기·DB·네트워크 시간이나 전체 로그인 지연의 원인별 비율을 나타내지 않는다. 인증 보안 반복 횟수는 변경하지 않았다.

시험용 풀 8은 이번 반복에서 로그인 거부를 없앴지만, 64명에서 성공 로그인 p95는 약 0.8초였다. 실제 서비스 수용 인원이나 최적 DB 풀 크기를 확정할 근거는 아니다. 5초 간격 서버 지표는 짧은 피크를 놓칠 수 있으며 DB 연결 보유 시간은 SQL 단일 쿼리 시간이 아니다.
