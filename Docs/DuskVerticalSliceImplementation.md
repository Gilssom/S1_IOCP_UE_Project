# Terra–Dusk server-authoritative combat vertical slice (2026-09-17)

## Implementation state

This is an implementation record, not a completed gameplay acceptance test. The external IOCP `GameServer` is the sole authority for Dusk spawning, movement, target choice, attacks, HP, death and respawn. Unreal presents server events. Q remains presentation-only; E, guard and dodge were not added.

- The server creates one Dusk melee minion for its Room when the first player enters. The original test spawn was `(0, 600, 100)`, facing `-90°`, on the flat MainMap floor. The 2026-09-22 grounding revision below replaces that historical Z value with the capsule-derived center Z. MainMap's test wall occupies approximately `X 372..628, Y -300..300`, so the initial player-to-minion line is unobstructed. This is a temporary test coordinate, not persistent content or DB data.
- Dusk: HP 200, speed 220 cm/s, acquisition 800 cm, home leash 1200 cm, target-loss distance 1000 cm, attack start at 170 cm, one server-resolved hit per action for 10 damage, no faster than 2 seconds and after the prior 1-second attack has ended. Dead despawns after 3 seconds and respawns with a new ObjectId 8 seconds after death. Return is invulnerable and resets HP on reaching home.
- Terra A–D server contact checks resolve once per accepted action: 25 damage against this one Dusk, at most 230 cm horizontal range, 160 cm height difference and a forward dot product of at least 0.34. Monster hit checks use 190 cm, 150 cm and 0.57 respectively. Range and direction are checked at the contact time, not merely at windup. The server checks action sequence, combo step order, minimum interval and live Room membership. This is a first-pass geometric hit volume, not weapon tracing or obstacle-aware combat.
- Server packets now distinguish stable monster definition ID `1`, per-spawn ObjectId and per-attack action instance ID. Spawn snapshot includes a monster and HP/state; update, attack, damage and player-status packets drive client presentation. The same Room serial queue owns gameplay state; no Unreal RPC/Replication authority was added.
- S1's `US1WorldEntitySubsystem` owns the visual monster keyed by server ObjectId, including late snapshots and despawn. `AS1DuskMinion` uses the user-added Dusk mesh and original idle/jog/Attack_A/death sequences with native single-node playback. The floating label shows HP and RETURN/DEAD. Player HP/death/respawn have a minimal text display. No map or imported binary asset was saved.
- An S1 AnimBlueprint was attempted through exposed MCP tools but could not be completed with a target skeleton and AnimGraph. The unsaved attempt was deleted. Single-node playback is deliberately temporary; attack-to-idle transitions depend on server state events and do not provide blend quality or additive hit reaction.

- Root cause of the short unnatural post-attack motion: after each one-second attack, the server unconditionally emitted `CHASE`, then emitted `IDLE` on the next 100 ms Room tick if the player was still in range. The presentation therefore played `Attack → Jog → Idle`. The server now selects `IDLE`, `CHASE`, or `RETURN` directly at attack completion.
- The client defers non-death animation switches until the full `Attack_A` length plus the Blueprint grace value has elapsed. Actor yaw also remains locked for that visual interval. Death still interrupts immediately.
- The Blueprint compiled with warnings treated as errors. A transient MainMap instance verified the generated class uses the Dusk mesh, relative mesh yaw `+90°`, scale `1`, mesh Z `-88`, capsule `40×88`, and single-node animation mode. It was removed and MainMap was not saved.
