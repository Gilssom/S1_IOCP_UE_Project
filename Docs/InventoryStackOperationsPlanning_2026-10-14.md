# 인벤토리 교환·합치기·분할 기획 검토

## 후속 완료 인계 반영 — 2026-10-14

아래 초안의 미승인·미구현 상태는 과거 기록이다. 최신 근거는
AstraCompletionHandoff_2026-10-14.md 및 InventoryStackOperationsImplementation.md다.
사용자 승인 후 교환·합치기·분할 구현과 사용자 테스트 완료가 보고됐다.
확정 조작은 일반 드래그 동일 포션 최대 99 합치기/잔량 유지, Ctrl 교환,
Shift 빈 칸 수량 분할이며 20칸 사용/80칸 표시는 유지한다.

후속 버리기는 플레이어가 버린 포션만 공용 필드 드랍으로 전환됐다.
몬스터 드랍 소유권은 유지한다. 신규 1039/1040 및 DB 3테이블이 적용됐으며
이전 영구삭제 경로로 자동 대체하지 않는다. 전량 획득, 동시 획득 1명,
미획득 30초 만료 정책이다. 시간대 만료 오류 수정 후 사용자 2인 PIE에서
양쪽 표시→타인 G 획득→양쪽 제거 및 30초 만료를 확인했다.
G 안내 WBP_S1LootPickupPrompt 분리도 구현 및 사용자 테스트 완료로 전달됐다.
키캡 PNG는 외부 디자인 Candidate이며 Unreal 적용 완료로 간주하지 않는다.

인계 문서 기준 빌드·자동 테스트 26개·패키징·새 WBP 클래스 로드는 통과했다.
이 기획 갱신에서 검증을 재실행하지 않았다. 실제 패키지 2계정 통합,
구버전 호환/네트워크 장애 주입, 최종 UI DPI 가독성 및 기존 인증 포커스 오류는
잔여 항목이다. 사용자 PIE 확인을 이 항목들의 완료로 확대하지 않는다.
이후 변경은 기존 8d6e0cc 커밋에 포함되지 않으며 새 커밋·푸시 완료로 보지 않는다.
서버 종료는 구현 담당 채팅의 사용자 요청이며 이 문서 갱신에서 실행하지 않는다.

다음 권장 순서: 인증 포커스 오류의 좁은 수정 → 최신 서버/클라이언트 패키지
2계정 통합 → 영상 시나리오와 서버·DB 증거 정리. 신규 콘텐츠는 별도 결정한다.

## 현재 기준

- UI 8×10칸 중 실제 저장공간은 20칸, 나머지는 잠금. 회복 포션 스택 상한 99.
- 더블클릭 사용, 퀵슬롯 드래그 등록/우클릭 해제 및 빈 칸 이동은 구현됐다.
- 빈 칸 이동의 위치·수량 유지와 재접속 등 요청된 PIE 체크는 사용자 확인 완료.
  확인 인원 수가 명시되지 않아 새로운 2인 테스트로 기록하지 않는다.
- 10/12 빌드·자동 테스트 23개·격리 DB 검사·패키징 성공은 당시 증거다.
  최신 패키지 2계정 통합, 주입 지연/끊김, HP 최종 가시성·재접속은 별도 미검증.
- 객체 HP 및 Dusk 복귀 중 HP 유지 재교전/집에서 4초 회복은 구현 상태다.
  Dusk 재교전·회복은 사용자 1인·2인 확인 완료이며 모든 HP UI 인수를 뜻하지 않는다.
- 생성한 판타지 UI PNG는 제작 후보이며 임포트·적용·최종 디자인 승인으로 보지 않는다.
- S1 커밋/푸시는 구현 담당이 진행 중이라고 전달받았으며 완료 해시는 미확인이다.
  GameServer 기존 스테이징은 이번 커밋 범위 밖이다. Content는 별도 백업 대상이다.

## 최소 동작 제안 — 사용자 결정 전

| 조작 | 제안 결과 |
| --- | --- |
| 일반 드래그 → 빈 사용 가능 칸 | 기존 스택 전체 이동 |
| 일반 드래그 → 같은 정의의 스택 | 목적지를 99까지 채우고 초과분은 원래 칸에 유지 |
| 일반 드래그 → 다른 정의의 스택 | 두 스택의 칸 교환; 수량·아이템 ID 유지 |
| 일반 드래그 → 이미 99인 같은 스택 | 변경 없음; 가득 찼다는 안내. 자동 교환하지 않음 |
| Shift+드래그 → 빈 사용 가능 칸 | 수량 선택 후 분할. 기본값은 절반 내림, 범위 1..원본 수량-1 |
| Shift+드래그 → 점유 칸 | 분할 거절. 합치기/부분 이동으로 자동 전환하지 않음 |
| 자기 칸·잠금 칸·창 밖·취소 | 변화 없음, 소비·폐기·지면 드랍 없음 |

사용자가 결정할 부분은 위 조작의 의미, 특히 동일 포션의 합치기 우선 정책과
Shift 분할의 수량 선택 방식이다. 현재 포션 한 종류만 있으므로 다른 정의 간
교환은 플레이 영상에서 자연스럽게 시연하기 어렵다. 교환 검증만을 위해 신규
아이템을 제작하지 않고 격리 테스트로 검증하는 것을 권한다.

## 소유권과 구현 경계

- UI는 드래그와 수량 입력을 수집하고 InventorySubsystem으로 요청한다.
  서버 승인 전 슬롯·수량을 확정 변경하지 않는다. DB·패킷 처리는 UI 밖에 둔다.
- IOCP/DB가 소유자, 슬롯, 수량, 스택 호환성, 최대치, 예약 및 버전을 검사한다.
  수량 합계가 보존되어야 하며 픽업 보상/소비/회복 이벤트로 취급하지 않는다.
- 전체 연산과 인벤토리 버전 증가는 하나의 트랜잭션으로 성공 또는 실패한다.
  UNIQUE(character_id,slot_index)를 지키는 교환 방법은 구현 담당이 결정한다.
  임시 슬롯을 사용한다면 중간 상태가 커밋되거나 클라이언트에 노출되어서는 안 된다.
- 완전 합치기는 목적지 ID를 유지하고 원본 스택을 제거한다. 부분 합치기는 두 ID를
  유지한다. 분할은 원본 ID를 유지하고 새 ID를 생성한다. 예약된 스택은 보호한다.
- 퀵슬롯은 정의 ID 등록을 유지한다. 합치기로 기존 스택 ID가 사라져도 현재 유효한
  스택을 다시 찾아 사용해야 한다. 새 스택 선택 우선순위 변경은 필요하지 않다.
- expectedVersion CAS, 기존 캐릭터 잠금 순서, 사용/획득 공통 대기 차단을 재사용한다.
  수량 선택 도중 상태가 바뀌면 제출을 취소하거나 최신 목록을 다시 확인하게 한다.
- 미확정 응답은 실패로 단정하지 않고 목록 재조회로 조정한다. 새 요청 자동 재전송은
  하지 않는다. 닫기·재접속 및 늦은 응답의 세션 필터를 유지한다.
- 기존 1033/1034의 의미를 조용히 바꾸지 않는다. 협상·요청 연산/수량·응답과 구버전
  동작을 포함한 최소 계약을 별도 제출한다. 이 문서는 새 패킷 번호를 확정하지 않는다.
- DB 일반 재설계, 폐기, 80칸 확장, 새 아이템·몬스터·퀘스트는 범위 밖이다.

## 단계별 인수 조건

1. 합치기: 원본 30/목적지 80 → 11/99. 10/80 → 원본 제거/90.
   목적지 99는 불변. 두 경우 모두 총량 불변이며 재접속 결과가 같다.
2. 분할: 10개 중 4개 → 원본 6/새 칸 4, 서로 다른 ID.
   1개 스택, 0·음수·전체 이상 수량, 잠금/점유 칸은 거절되고 총량 불변.
3. 교환: 격리 fixture의 서로 다른 정의 두 스택이 슬롯만 맞바뀐다.
   UNIQUE 충돌이나 중간 실패 시 전부 롤백된다. 실제 포션만으로 이 검증을 대체하지 않는다.
4. 경쟁/복구: 같은 버전의 동시 요청은 최대 하나만 반영. 소비 예약 중 변경 거절.
   오래된 버전, 외국 캐릭터 ID, 중복 요청, COMMIT 후 응답 유실·재접속에서도 복제/소실 없음.
   로그로 실제 커밋과 화면 동기화를 구분하고, 미실행 장애 테스트는 미검증으로 남긴다.
5. 1인 PIE: 조작·취소·재열기·재접속·퀵슬롯 재사용·더블클릭·입력 복귀를 확인한다.
   분할 창 입력이 전투나 퀵슬롯 소비를 유발하지 않아야 한다.
6. 2인 PIE/최신 패키지: 두 계정의 인벤토리 독립성, 다른 플레이어의 전투/드랍에
   영향 없음, 서버 승인 후 각자 수량 및 재접속 복원을 확인한다.

기존 WBP_S1InventoryGrid/Slot 및 포션 아이콘을 재사용하고 수량 입력 UI만 필요하다.
실제 수정 파일과 새 WBP 경로는 구현 조사 후 확정한다. 바이너리 변경 전 부분
체크포인트, 변경 에셋 선택 저장 및 사용 변경 시 자산 목록 갱신이 필요하다.

## 포트폴리오 우선순위

세 기능은 인벤토리 조작을 완성하는 제한된 후속 작업으로 묶는다. 이후 기능 확대보다
HP 가시성 잔여 인수, 로그인 포커스 오류, 최신 서버/클라이언트 패키지 2계정 통합,
영상 및 서버·DB 증거 정리로 돌아간다. 일정·완료율은 근거 없이 산정하지 않는다.
